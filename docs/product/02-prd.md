# PRD: from idea to a shipped application

Status: draft. Scope: the single journey a new user takes from typing an idea to deploying something usable.

Related: [strategy](./01-strategy.md), [metrics](./04-metrics.md), [AI evaluation](./05-ai-evaluation.md), [roadmap](./06-roadmap.md).

Each requirement carries a status for the current repository: Built, Partial, or Not built. "Built" always means the interface works with scripted content. Nothing is generated by a real model, because there is no model.

## Problem and context

People with an app idea stop at the blank prompt box. Even those who get past it cannot tell whether what comes back matches what they meant, or what the AI decided without telling them. See [strategy](./01-strategy.md) for the reasoning. These remain hypotheses until the interviews in the [discovery plan](./03-discovery-plan.md) are done.

The journey this PRD covers: idea, clarify, plan, approve, build, preview, change, deploy.

## Target user

Primary: Maya, a non-technical founder who can describe an idea in plain words. She should be able to finish the journey without seeing code.

Secondary: Dev, a developer. He should be able to open the same journey and see owners, reasons and dependencies. He is served by the technical-detail toggle and the Code and Ship tools, which are read-only or simulated today.

Example used throughout: "A platform where tutors create profiles and students book demo classes."

## Goals

Outcome targets are proposals to calibrate after the first usability sessions. None has been measured.

1. A new user reaches an approved plan in under three minutes without help.
2. A user can state who is doing what and what needs them, within five seconds, from a mid-build screen.
3. The delivered preview matches the approved plan. Every feature on the plan card is findable in the result.
4. Failures are explained as consequences, not stack traces, and the user always has a next step.
5. A user can stop, change direction or undo without losing work.

## Non-goals

No custom agents, no team accounts, no real billing, no mobile app. No code editing in this version (the Code view is read-only). No claim that simulated GitHub or Deploy are real. See [strategy non-goals](./01-strategy.md#non-goals).

## User stories

Maya, the creator:
- As a creator, I want the Manager to ask only what it needs, with sensible defaults, so I can move fast without knowing technical terms.
- As a creator, I want to review a plan in plain language before anything is built, so a misunderstanding costs me nothing.
- As a creator, I want the preview to grow while the team works, so I can see progress without reading logs.
- As a creator, I want to be asked only when a decision is really mine, so I am not interrupted by details.
- As a creator, I want to ask for a change in my own words and be told who owns it.
- As a creator, I want to publish and get a link I can share.

Dev, the developer:
- As a developer, I want to see each task's owner, reason and dependencies, so I know why the AI did what it did.
- As a developer, I want to talk to one specialist privately, so I can question a decision without cluttering the main thread.
- As a developer, I want to see changes before they are applied, so nothing is overwritten silently.

## Requirements

### P0

R1. Clarify before planning. Status: Built, scripted (`clarifyFor` in `src/store/scripts.ts`, `ClarifyCard` in `src/components/chat/Cards.tsx`).
- Given a first message, when the Manager replies, then it shows at most three questions, each with a default already chosen.
- Given the clarify card is open, when the user types a message instead, then the defaults are used and the plan appears.
- Given the user presses "Let the Manager decide", then the card collapses to "Manager used its defaults".
- Answers that add features appear on the plan card and survive plan revisions.

R2. Reviewable plan and approach. Status: Built, scripted (`PlanCard`, `StrategyCard`).
- Given a plan, when the user presses Adjust and submits a note, then a revised plan appears with its revision number.
- Given three approaches (Lean, Balanced, Enterprise), when the user picks one, then the task list reflects it. Lean has 3 tasks, Balanced 5, Enterprise 7 (`STRATEGY_TASKS` in `src/store/store.ts`).
- Nothing is built until "Start building" is pressed.

R3. Visible ownership during the build. Status: Built, scripted (`TeamStrip`, `BuildCard`, and the `dependsOn` and `why` fields on `BuildTask` in `src/store/types.ts`).
- Given a running build, each active specialist shows a status of working, needs you, done or failed.
- Given "Show technical detail" is on, the build card lists every task with owner, reason and what it waits on.
- Only the newest build card is shown in the thread.

R4. A decision that pauses the build. Status: Built, one scripted question (`DecisionCard`, `answerDecision`).
- Given Balanced or Enterprise, when QA reaches review, the build pauses and one card asks the user to choose.
- Given the user chooses, the build resumes and the card collapses to a one-line record.
- Lean never pauses.
- Pressing "Start building" twice must not start a second build.

R5. Preview that matches the plan. Status: Partial. Preview templates exist for a habit tracker, a client portal and a price comparison board (`src/components/preview/docTemplate.ts`). A tutor marketplace idea gets the habit tracker preview, because `pickTemplate` in `src/store/store.ts` has no marketplace branch. This is a plan-to-result mismatch, and a careful reviewer would notice it first.

R6. Honest error and recovery. Status: Partial. The preview has an error state and the Deploy view has a failure path, but no code in the store ever sets a build to the error state, so build failure cannot be reached. Production deploy always fails by design, to show the failure UI.
- Given a failed build, the message says what the user cannot do yet, not only the technical cause, and offers retry.

R7. Deploy with a way back. Status: Built, simulated (`src/components/deploy/DeployView.tsx`).
- Rollback adds a new version that points at the chosen one. History is never rewritten.

### P1

R8. Survive a reload. A reload during a build currently leaves it stuck, because timers are not persisted (a known gap listed in [`docs/blueprint.md`](../blueprint.md)). A resumed build should either continue or say clearly that it stopped.

R9. Edit and diff in Code, with Guard findings marked Advisory or Blocking. Not built. Code is read-only and Guard checks are canned and advisory.

R10. Canvas changes create a task for the right specialist. Not built.

### P2: design for it, do not build it

A real agent runtime behind an interface, real sandboxes, real GitHub, multi-user projects. See the [roadmap](./06-roadmap.md).

## States, failures and edge cases

Vague idea: the Manager should still ask rather than guess. Today a vague idea falls to the generic plan branch ("Core create and list flow").

Message during a build: it should reach the Manager and be routed, not ignored.

Reload mid-build: see R8.

Two browser tabs: state lives in `localStorage` and nothing listens for changes from another tab, so the last write wins.

One specialist fails: the build should name the failed task and let the user retry that task. Not built.

Conflicting answers: if a clarify answer contradicts the original idea, the Manager should say so. Not built.

## Dependencies and constraints

Today the whole journey is scripted in the browser. A real version depends on a model provider, a sandbox to run generated code, persistence beyond `localStorage`, and a runtime that can pause for a human decision. The proposed shape is in [`docs/architecture/production-architecture.md`](../architecture/production-architecture.md). The first step is an `AgentRuntime` seam, so the interface survives the swap (see [`docs/blueprint.md`](../blueprint.md)).

## Accessibility, privacy and control

Status colour is never the only signal. The Team strip pairs colour with a label and a tooltip. Motion respects `prefers-reduced-motion`, and interactive elements show a focus ring.

Privacy: nothing leaves the browser today. In a real version, generated code would run in an isolated sandbox, secrets would be injected at runtime and never put in model context, and imported repositories would be written only on a branch.

Control: the user approves the plan before building, can adjust it, and can answer or skip clarifying questions. Stopping a build is not built yet.

## Open questions

Who is the first real user, Maya or Dev? This decides what gets built after the prototype. Owner: founder.

Should a private DM be visible to the Manager? Proposed: a one-line activity note only. Owner: product.

Are Lean, Balanced and Enterprise the right names for non-technical users? Owner: design.

What does success mean for a deployed app: that it worked, or that the user kept using it? See [metrics](./04-metrics.md). Owner: product and data.
